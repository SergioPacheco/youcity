# YouCity blog design

**Date:** 2026-09-20

## Goal

Add a small, static, English-language editorial blog to YouCity without
loading the interactive application on blog pages. The public routes are
`/blog` and `/blog/<slug>`, with extensionless canonical URLs and static HTML
generated by the existing build.

The blog helps visitors discover destinations, understand virtual city
exploration, and use YouCity's existing video and radio experiences. It does
not claim current conditions, universal mode availability, ownership of
third-party media, or search-ranking outcomes.

## Constraints and existing architecture

- Keep the current vanilla HTML/CSS/Node static architecture.
- Do not add a framework, database, runtime dependency, client-side blog
  bootstrap, comments, login, search, pagination, player, radio, map, or
  sharing library to blog pages.
- Do not add a package dependency. The build runs with the repository's
  current Node.js APIs and installed `jsdom` test dependency only.
- Preserve the existing interactive home/city build, consent modules, legal
  pages, Cloudflare files, base-path handling, and city sitemap coverage.
- Do not publish automatically.

## Content source and rendering

Articles live in versioned files under `content/blog/*.md`. Each file contains
a simple YAML-like frontmatter block delimited by `---` and a Markdown body.
The build-only renderer is intentionally limited to the authored syntax needed
by the blog:

- paragraphs;
- ATX headings limited to H2 and H3;
- unordered and ordered lists;
- emphasis and strong emphasis;
- inline links with validated destinations;
- optional blockquotes for editorial caveats.

The renderer is a line/state tokenizer, not a collection of regular-expression
substitutions. It rejects unsupported or malformed constructs instead of
guessing. Raw HTML, inline HTML, images in article bodies, scripts, event
attributes, and arbitrary protocols are not accepted. Text is escaped before
being emitted. Links are emitted only for HTTPS external URLs or validated
site-relative internal URLs; external links use `target="_blank"`
and `rel="noopener noreferrer"`.

Frontmatter parsing is similarly strict: only documented scalar fields,
booleans, ISO dates, and string arrays are accepted. Values are decoded as
data, never evaluated. Unknown keys, duplicate keys, invalid quotes, unsafe
slugs, invalid dates, malformed arrays, or missing required fields fail the
build with the source filename.

Required article fields are `title`, `slug`, `description`, `image`,
`imageAlt`, `author`, `datePublished`, `relatedCities`, `relatedPosts`, and
`draft`. Optional fields are `dateModified`, `sources`, `imageCredit`, and
`ctaLabel`. A published article must have a non-future `datePublished`, a
local existing cover image, at least one valid related catalog city, and a
complete body. A draft or future article is parsed and validated but omitted
from generated HTML, the listing, related links, sitemap, and public content
assets. References to drafts are ignored rather than rendered as broken links.

## Build integration

Add a build-only module under `scripts/` that:

1. reads and validates all blog source files;
2. filters drafts and future dates using the build clock;
3. resolves catalog cities with the existing `slugify` rule;
4. verifies local cover images and related published articles;
5. renders `/blog/index.html` and `/blog/<slug>.html` from shared templates;
6. returns the public article metadata to the main build;
7. adds `/blog` and each published article to the sitemap.

The main build calls this generator after `dist/` is created and static assets
are copied, before sitemap generation and final validation. Blog templates use
their own small stylesheet and a minimal header, so they do not reference
`src/main.mjs`, `src/catalog/catalog.mjs`, or the interactive `styles.css`.
Shared legal URLs and all root-relative URLs are passed through the existing
`SEO_BASE_PATH` handling. Canonicals, social URLs, JSON-LD URLs and sitemap
locations use `SEO_SITE_URL` plus `SEO_BASE_PATH`.

The extensionless public URL is canonical while the generated `.html` file is
the static-host artifact, matching the current Cloudflare Pages behavior used
by city pages. No catch-all fallback is added for unknown blog slugs; the
existing custom 404 remains the not-found response.

## Templates and SEO

The blog listing has a minimal header with the existing YouCity identity,
`Explore cities`, and `Blog` links; it renders H1 `Travel inspiration`, a
short introduction, and a responsive card grid. Each public article renders a
breadcrumb, cover image, H1, description, author/date, full article body,
contextual city CTA, two or three published related articles, and existing
privacy/terms footer links.

Each generated document has `lang="en"`, unique title and description,
absolute canonical, Open Graph and Twitter metadata, `og:type="article"`
for posts, an absolute cover image URL, visible H1, and one safely serialized
JSON-LD script. Post JSON-LD uses an `@graph` containing `BlogPosting` and
`BreadcrumbList`; the listing uses `CollectionPage` and an `ItemList` for the
articles actually shown. JSON-LD serializes `<` as `\\u003c` before insertion
into the script element.

Cover markup uses real local files with known dimensions and `srcset` only for
variants that exist. The first cover is eager/high-priority; no below-fold
article-body images are needed for the initial version. Credits and source
notes are visible or documented when required by the asset license.

## Initial editorial set

Publish two complete examples whose claims can be supported by the verified
YouCity catalog and cited sources. Use the existing project cover for a
general virtual-exploration article where it is editorially appropriate, and
use a clearly labelled non-documentary project-created illustration for the
second complete article if no permitted destination photograph is available.
Do not present an illustrative image as evidence of a place.

Create ten additional structured files with `draft: true`, each recording a
distinct audience/question, proposed title and slug, intended related city or
experience, sources needed, image/license requirement, and CTA. They remain
out of the public build until editorial review completes them. The set covers
virtual exploration, selected catalog cities, beach selection, walk versus
drone, local radio, destination comparison, city breaks, and a travel-video
checklist without presuming unavailable modes.

## Styling and accessibility

Blog CSS reuses the current dark palette and green accent values as copied
tokens, keeps body scrolling enabled, and provides a readable central article
column. The listing uses three columns on wide screens, two below 900px, and
one below 600px. Article content is comfortable at 320px without horizontal
overflow. Links are visibly identifiable without color alone; focus-visible
states have a high-contrast green outline; image dimensions prevent layout
shift; motion is minimal and disabled under `prefers-reduced-motion`.

The existing home navigation receives a real `Blog` link in desktop and mobile
navigation without changing the primary city experience. Blog navigation works
with JavaScript disabled.

## Validation and documentation

Add focused blog tests for frontmatter, slugs, future/draft exclusion, local
assets, metadata uniqueness, safe HTML/JSON-LD, related links, sitemap exactness,
and base paths. Extend `scripts/seo-check.js` without weakening city checks.
Extend build-output tests to assert the blog artifact and absence of the
interactive bootstrap from blog documents. Keep existing commands passing:

```text
node scripts/build-static.js
node scripts/seo-check.js
npm run seo:test
npm run build:validate
npm test
```

Add `docs/blog.md` with article creation, fields, image credits, relationships,
draft/future behavior, preview and validation, slug migration redirects, and
post-publication Search Console/Rich Results checks. Visual checks cover 320px,
390px, 768px, desktop, keyboard navigation, JavaScript disabled, normal
scrolling, and absence of interactive media modules. No Lighthouse score is
reported unless a real available tool is run.

## Alternatives rejected

- Reusing the interactive `index.html` for posts: it would load unrelated
  application code and make the initial HTML less focused.
- Adding a runtime Markdown package or browser hydration: unnecessary for
  static output and contrary to the performance/dependency constraints.
- Generating article content from JavaScript: not crawlable without execution
  and contrary to the SEO requirement.
- Publishing all twelve skeletons: creates thin, incomplete public pages and
  fails the editorial-quality requirement.
